# Segmental evidence and replay boundary

This is a source/provenance audit, not a live-provider evaluation. No speech provider was called.

Azure `AzurePronunciationProvider.assess()` sends canonical recording audio plus `ReferenceText=request.target_snapshot["text"]`, Mandarin zh-CN, HundredMark grading, Phoneme granularity, Comprehensive dimension, EnableMiscue and SAPI alphabet. `Words[].Phonemes[]` is normalized as `phone`, `pronunciation_score` from AccuracyScore, optional seconds-based `timing` (Offset/Duration divided by 10,000,000), and `provider_assessment`. Both nested and flat assessment fields are supported. Word-level output is stored under `AssessmentEvidence.syllables`, despite originating from provider **words**, not guaranteed syllables. A score describes reference-relative match; it is not a recognized alternative phone or proof of which substitute was spoken.

The current [Microsoft documentation](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/how-to-pronunciation-assessment) confirms phoneme-level accuracy and zh-CN SAPI phoneme names. This supports the adapter's capability, not accuracy on these four recordings. The adapter can supply target-relative phone evidence independently of ASR Hanzi; it does not yet supply a calibrated initial/final grade. Mandarin phone grouping, word-to-syllable mapping, missing phone timings, provider errors and omission/insertion behavior need explicit handling. Multi-character words cannot be indexed as if they were guaranteed individual syllables.

`AssessmentEvidence.normalized()` retains `syllables` with untyped nested dictionaries, plus separate overall/pronunciation/phone/tone scores where available. AssessmentRun persists provider/product/adapter version, normalized result, raw provider payload and hash, status, timing and target snapshot lineage. The result API includes the assessment run's normalized result; eligible live syllable dictionaries can also appear as `PronunciationSyllableResult.provider_evidence`. Mobile types permit this data, but the current feedback component does not render phone-level grades. No new schema or Sounds card was added.

For iFLYTEK, the XML normalizer preserves phone `content`, `is_final` from `is_yun`, `phone_score`, reference tone, phone error classifications, perr metadata, positional timing and original phone attributes. It keeps syllable phone and tone scores separately. Tencent fixture/live normalization retains PhoneInfos/PhoneInfo, phone/reference_phone, PronAccuracy, MatchTag, ReferenceLetter, converted millisecond timing and provider_phone. These provider-specific schemas are evidence containers, not interchangeable calibrated grades. Fixture normalization tests prove mapping only, not human validity.

The four fresh attempts use **replay target assessment**: synthetic pronunciation_score=79, no genuine phone assessment. This is absence of live assessment evidence, not hidden live phone evidence. The fixture warning stays scoped to assessment; replay/unknown assessment syllables are excluded from learner tone feedback. Numerical target accuracy is only rendered for successful `live_provider` assessment with an acceptable recording. Local F0 and observed contour do not consult that score.

The fresh recordings contain real locally extracted Praat F0, persisted OpenAI perception, and successful Azure alignment (`azure_sapi_syllable` spans). Alignment can carry reference phone labels; those labels are alignment hypotheses, **not a pronunciation score**. A reference label `tian 1` is not evidence that /t/ was correct. Likewise 钱。 is the ASR perception, not evidence sufficient to say “your t sounded like q.” ASR may be influenced by lexical probability, acoustic ambiguity, short context or other factors; these artifacts cannot isolate the cause.

Before a trustworthy Sounds grade: obtain explicitly authorized live target assessments on controlled real recordings; map provider phone identities to Mandarin initials/finals and target syllables; validate alignment, omissions, insertions and phonetic inventory; maintain separate tone and segmental provenance; calibrate thresholds and uncertainty against independent human labels across speakers, devices and noise; test tian/qian and homophonous-character controls; define unavailable/uncertain outcomes and provider disagreement handling. Do not derive correctness from text equality or from a generic provider total score. No live validation, score calibration or segmental UI occurred here.
